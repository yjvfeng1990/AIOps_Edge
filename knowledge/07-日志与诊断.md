# 日志与诊断

> 来源：《edgeos-edge-runtime-plan.md》《edgeos-driver-framework-advanced-plan.md》《使用手册》

## 三级日志架构

1. **串口日志**：P4 UART0（GPIO37/38，115200）、C6（GPIO16/17）。所有 `ESP_LOGx` 输出。串口日志经 logs_vprintf 钩子同时镜像进 Web 日志系统
2. **Web 日志中心**：PSRAM 环形缓冲（256KB 滚动）+ LittleFS JSON 文件（system_log.json）+ 7 天轮转；四类日志（系统/设备/自动化/安全）统一中心
3. **审计日志**：49 处 audit_log 覆盖关键操作（登录/配置修改/设备删除/OTA 等），存 /spiffs/logs，Web 后台可查（系统设置 → 审计日志）

查看方式：
- Web：系统设置 → 系统日志（支持级别过滤与分页），或 API `GET /api/v1/logs`
- 下载：`GET /api/v1/logs/download`
- 清理：`POST /api/v1/logs/cleanup`

## Edge Runtime 监控（Web 调试中心 / API）

| 能力 | API | 说明 |
|------|-----|------|
| 系统健康 | `GET /api/v1/system/health` | health_mgr 24 槽位，状态 OK / DEGRADED / CRITICAL |
| 组件健康明细 | `GET /api/v1/system/health/components` | 每个服务/驱动的健康状态 |
| 资源监控 | `GET /api/v1/system/resources` | resource_mgr 5s 采集，内存阈值告警 |
| 任务监控 | `GET /api/v1/system/tasks` | task_mgr：每个任务的栈水位（min free stack）与运行时长 |
| 定时器 | `GET /api/v1/system/timers` | timer_mgr 管理的定时器列表 |
| 驱动诊断 | `GET /api/v1/drivers/diag` | 8 槽位驱动诊断：读写次数/错误计数/平均延迟 |
| 系统信息 | `GET /api/v1/system/info` | 固件版本/编译时间/IP/运行时长 |

## 诊断方法论

1. **先看健康总览**：`system/health` 是否有 DEGRADED/CRITICAL 组件
2. **看资源**：`system/resources` 内存是否接近阈值（PSRAM 大量占用会触发告警）
3. **看任务栈水位**：`system/tasks`，min stack < 1KB 的任务有栈溢出风险（历史上 mqtt_task 曾因日志钩子栈溢出，#196/#197 已修复：栈 32KB + 钩子缓冲静态化）
4. **看驱动诊断**：`drivers/diag`，错误计数增长 → 检查接线/从站地址/串口参数
5. **看告警与日志**：`alarms` + `logs` 定位时间线
6. **必要时上串口**：`idf.py -p COM9 monitor` 看原始输出（含复位原因 rst:0xXX）

## 复位原因（串口启动日志第一行）

| 复位码 | 含义 | 常见场景 |
|--------|------|----------|
| rst:0x1 POWERON | 上电复位 | 正常断电重启 |
| rst:0x10 LP_WDT / RTCWDT | 看门狗复位 | SDIO init 期间已知问题（见故障 FAQ） |
| rst:0x12 SW_CPU | 软件复位 | OTA 升级切换、esp_restart |
| SW_RESET | 软重启 | 崩溃后 abort/panic |
